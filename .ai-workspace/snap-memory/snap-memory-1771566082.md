## CODE ARCHITECTURE

### New Test Infrastructure Components

#### BaseUnitTest
**Purpose**: Common base class for all unit tests
**Public API**:
- `@Mock protected MeterRegistry meterRegistry` - Auto-configured with Counter/Timer mocks
**Pattern**: Extend with `@ExtendWith(MockitoExtension.class)`

#### BaseIntegrationTest
**Purpose**: Base class for integration tests with sample rule loading
**Public API**:
- `loadSampleRules()` - Load rules from /sample-rules/
- `loadSampleRule(String ruleId)` - Load specific rule
**Pattern**: Extend with `@SpringBootTest`

#### RuleTestUtils
**Purpose**: Static utility methods for test data creation
**Public API**:
- `createSimpleRule(String ruleId)` - Create valid test rule
- `createInvalidRule(String ruleId)` - Create invalid rule (missing package)
- `loadRuleFromFile(String path)` - Load .drl file from disk
- `createTestData(Object... keyValuePairs)` - Create test data maps

#### ValidationConfigTestHelper
**Purpose**: Create ValidationConfig with test values using reflection
**Public API**:
- `createTestValidationConfig()` - Returns configured ValidationConfig
**Why Needed**: ValidationConfig uses @Value injection, can't be instantiated normally

#### TestValidationConfig
**Purpose**: Spring @TestConfiguration providing beans for @WebMvcTest
**Public API** (Beans):
- `ValidationConfig validationConfig()` - Uses ValidationConfigTestHelper
- `MeterRegistry meterRegistry()` - Returns SimpleMeterRegistry
- `Validator validator(ApplicationContext)` - Configures SpringConstraintValidatorFactory
**Usage**: Add `@Import(TestValidationConfig.class)` to @WebMvcTest classes

## PROBLEM SOLVING

### Error 1: ValidationConfig Null in RuleIdValidator

**Error Message**:
```
NullPointerException: Cannot invoke "ValidationConfig.getRuleIdMaxLength()"
because "this.validationConfig" is null
```

**When**: Running RuleExecutionControllerTest and AdminControllerTest

**Root Cause**:
- @WebMvcTest creates minimal Spring context
- RuleIdValidator has `@Autowired ValidationConfig`
- Hibernate Validator creates RuleIdValidator instances without Spring's bean factory
- Need SpringConstraintValidatorFactory to inject Spring beans into validators

**Solution Applied**:
1. Created ValidationConfigTestHelper to instantiate ValidationConfig via reflection
2. Created TestValidationConfig providing ValidationConfig bean
3. RuleExecutionControllerTest: Added @Import(TestValidationConfig.class)
4. AdminControllerTest: Changed to AnnotationConfigApplicationContext for better autowiring

**Prevention**: Always use AnnotationConfigApplicationContext for validator test setup

---

### Error 2: @MockBean Import Not Found

**Error Message**:
```
package org.springframework.boot.test.mock.bean does not exist
```

**When**: Compiling RuleExecutionControllerTest

**Root Cause**: Spring Boot 3.x changed package structure
- Old: `org.springframework.boot.test.mock.bean.MockBean`
- New: `org.springframework.boot.test.mock.mockito.MockBean`

**Solution**: Changed import to `.mock.mockito.MockBean`

---

### Error 3: RateLimitingFilter Bean Not Found

**Error Message**:
```
UnsatisfiedDependencyException: Error creating bean with name 'rateLimitingFilter'
No qualifying bean of type 'InMemoryRateLimitingService' available
```

**When**: Running RuleExecutionControllerTest

**Root Cause**: @WebMvcTest auto-configures all filters, but RateLimitingFilter needs InMemoryRateLimitingService which isn't available in slice testing

**Solution**: Added excludeFilters to @WebMvcTest:
```java
@WebMvcTest(
    controllers = RuleExecutionController.class,
    excludeFilters = @ComponentScan.Filter(
        type = FilterType.ASSIGNABLE_TYPE,
        classes = {RateLimitingFilter.class}
    )
)
```

---

### Error 4: MeterRegistry NullPointerException

**Error Message**:
```
NullPointerException: Cannot invoke "MeterRegistry$Config.clock()"
because return value of "MeterRegistry.config()" is null
```

**When**: Executing RuleExecutionController.executeRule() in test

**Root Cause**: @MockBean MeterRegistry was mock but not configured. When controller calls `meterRegistry.timer()`, it returns mock Timer which has null config()

**Solution**: Use SimpleMeterRegistry instead of mocking
- Created bean in TestValidationConfig
- Removed @MockBean from test class

**Why Better**: SimpleMeterRegistry is real, lightweight, needs no configuration

## DECISION LOG

### Decision 1: AnnotationConfigApplicationContext vs StaticApplicationContext

**Alternatives Considered**:
1. StaticApplicationContext - Simple, fast, minimal features
2. GenericApplicationContext - Mid-level, some autowiring
3. AnnotationConfigApplicationContext - Full autowiring support

**Chosen**: AnnotationConfigApplicationContext

**Rationale**:
- Better autowiring support needed for SpringConstraintValidatorFactory
- afterPropertiesSet() auto-configures validator factory
- More similar to real Spring Boot context

**Trade-offs**: Slightly heavier than Static, but still fast for tests

**Reversibility**: Easy to change, just swap context class

---

### Decision 2: SimpleMeterRegistry vs Mocked MeterRegistry

**Alternatives Considered**:
1. @MockBean MeterRegistry - Requires complex when() setup
2. SimpleMeterRegistry - Real implementation, no mocks needed
3. NoopMeterRegistry - Discards all metrics

**Chosen**: SimpleMeterRegistry

**Rationale**:
- No mocking complexity
- Real metrics collected (can verify in tests if needed)
- No configuration required

**Trade-offs**: Slightly more memory than noop, but negligible

**Reversibility**: Easy - just change bean type

---

### Decision 3: Real KieServices vs Mocked

**Alternatives Considered**:
1. Mock KieServices - Fast, isolated, complex setup
2. Real KieServices - Real compilation, slower, realistic

**Chosen**: Real KieServices

**Rationale**:
- Drools compilation is core feature - must be tested realistically
- Mocking KieServices too complex and fragile
- Performance acceptable (~1-2 seconds)

**Trade-offs**: Slower tests, but better confidence

**Reversibility**: Difficult - would require major test refactoring

---

### Decision 4: Testcontainers vs Mocked S3

**For Integration Tests**:

**Alternatives Considered**:
1. Mock S3Client - Fast, isolated, not realistic
2. Testcontainers LocalStack - Real S3 API, slower, realistic
3. Real AWS S3 - Most realistic, requires credentials, slow

**Chosen**: Testcontainers LocalStack

**Rationale**:
- Integration tests should test real integration
- LocalStack provides realistic S3 API
- No AWS credentials needed
- Reproducible across environments

**Trade-offs**: ~5 second LocalStack startup, acceptable for integration tests

### Gotchas & Pitfalls

1. **Never use StaticApplicationContext for validators** - AnnotationConfigApplicationContext required

2. **@WebMvcTest loads all filters by default** - Must exclude filters that need unavailable beans

3. **SimpleMeterRegistry > Mocked MeterRegistry** - Real implementation simpler than complex mocks

4. **afterPropertiesSet() must be AFTER setApplicationContext()** - Order matters for proper configuration

5. **ValidationConfig @Value fields need properties** - Must be in application-test.yml

6. **Testcontainers adds ~5 seconds** - Budget time for container startup in integration tests
