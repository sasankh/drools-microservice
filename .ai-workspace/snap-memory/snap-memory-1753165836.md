## 🛠️ **HOW** - Technical Implementation Details and Approach

### **Validation Architecture**
```
Request → @Valid Annotation → Custom Validators → ValidationConfig → Environment Variables
         ↓
    Field Validation → Pattern Matching → Size Checks → Security Filters
```

### **Multi-layer Security Stack**
```
1. Server-level: Tomcat request size limits
2. Spring-level: Multipart and HTTP size limits  
3. Filter-level: Custom validation filters (Rate limiting, Size validation)
4. Controller-level: Bean validation with custom annotations
5. Application-level: Log sanitization across all components
```

### **Rate Limiting Strategy**
- **Sliding Window**: Time-based windows for per-minute and per-hour tracking
- **Memory Management**: Automatic cleanup of old entries to prevent memory leaks
- **Client Identification Chain**: API key → Bearer token → Client-ID → IP address
- **Header Compliance**: Standard HTTP rate limiting headers for client awareness

### **Sanitization Approach**
- **Pattern-based Detection**: Regex patterns for various sensitive data types
- **Context-aware Masking**: Different masking strategies (full redaction vs partial masking)
- **Performance Optimization**: Efficient string processing and caching of compiled patterns
- **Safe Logging**: Field count limiting and safe data representation methods

## 🎯 **DECISION LOG**

### **Architecture Decisions Made**

#### **1. Validation Framework Approach**
**Decision**: Custom Spring Boot validation annotations vs third-party validation library
**Chosen**: Custom annotations with Spring Boot validation
**Reasoning**: 
- Better integration with existing Spring Boot stack
- Full control over validation logic and error messages
- No additional dependencies required
- Environment-configurable validation limits

**Alternatives Considered**: Hibernate Validator extensions, Apache Commons Validator
**Trade-offs**: More code to maintain vs better integration and control

#### **2. Rate Limiting Implementation**
**Decision**: In-memory vs Redis-based vs Third-party service (Bucket4j)
**Chosen**: In-memory with automatic cleanup
**Reasoning**:
- No additional infrastructure dependencies
- Suitable for single-instance deployments initially
- Easy to extend to Redis later if needed
- Consistent with "independence" requirement

**Alternatives Considered**: Bucket4j, Redis-based, Hazelcast
**Trade-offs**: Single-instance limitation vs simplicity and independence

#### **3. CORS Configuration Strategy** 
**Decision**: Allow-all default vs Restrictive default
**Chosen**: Allow-all (*) default with full configurability
**Reasoning**:
- User explicitly requested: "allow all calls. if we want to restrict we want the capability but for now its *"
- Development-friendly default
- Production can be secured via environment variables

**Alternatives Considered**: Restrictive defaults, Domain-specific defaults
**Trade-offs**: Less secure defaults vs development ease and user requirements

#### **4. Log Sanitization Scope**
**Decision**: Comprehensive sanitization vs Minimal sanitization
**Chosen**: Comprehensive with 16+ patterns and multiple data types
**Reasoning**:
- Better compliance with privacy regulations
- Prevents accidental sensitive data exposure
- Configurable patterns for future extensibility

**Alternatives Considered**: Basic sanitization, External tools, No sanitization
**Trade-offs**: More processing overhead vs better security and compliance

### **Technical Trade-offs Made**

#### **Memory vs Persistence (Rate Limiting)**
**Trade-off**: In-memory rate limiting (faster) vs Redis persistence (distributed)
**Chosen**: In-memory for now
**Benefit**: Better performance, no external dependencies
**Sacrifice**: Single-instance limitation, rate limit resets on restart

#### **Validation Granularity vs Performance** 
**Trade-off**: Comprehensive validation (secure) vs Minimal validation (faster)
**Chosen**: Comprehensive validation
**Benefit**: Better security, attack prevention
**Sacrifice**: Minor performance overhead on request processing

#### **Environment Flexibility vs Default Security**
**Trade-off**: Flexible defaults (easy dev) vs Secure defaults (better prod)
**Chosen**: Flexible defaults with full configurability
**Benefit**: Developer-friendly, user requirements met
**Sacrifice**: Requires explicit production configuration
