## 🏗️ **ARCHITECTURE DECISIONS**

### **Design Choice 1: Centralized TimeoutConfig vs Distributed**
**Decision**: Single TimeoutConfig bean with all timeout values
**Alternatives Considered**: 
- Per-service timeout configuration classes
- Annotation-based timeout declarations
**Trade-offs Made**:
- ✅ **Benefit**: Single source of truth, easier maintenance
- ✅ **Benefit**: Environment-specific tuning in one place
- ⚠️ **Trade-off**: Slight coupling between unrelated components
- ⚠️ **Trade-off**: All timeouts loaded even if not used

### **Design Choice 2: Custom TimeoutException vs Generic**
**Decision**: Custom TimeoutException with operation context
**Alternatives Considered**:
- Java's TimeoutException with wrapper
- Generic RuntimeException with timeout message
**Trade-offs Made**:
- ✅ **Benefit**: Rich context (operation + timeout duration)
- ✅ **Benefit**: Type-safe exception handling
- ✅ **Benefit**: Better error messages and debugging
- ⚠️ **Trade-off**: Additional exception class to maintain

### **Design Choice 3: HTTP Filter vs Controller Aspects**
**Decision**: OncePerRequestFilter for request timeout monitoring
**Alternatives Considered**:
- AOP aspects on controller methods
- Interceptors in Spring MVC
**Trade-offs Made**:
- ✅ **Benefit**: Covers all HTTP requests uniformly
- ✅ **Benefit**: Standard servlet filter pattern
- ✅ **Benefit**: Early request processing
- ⚠️ **Trade-off**: Filter overhead on every request
