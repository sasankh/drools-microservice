
- **Code After**:
```java
// Dispose old KieContainer to prevent memory leak

KieContainer oldContainer = currentKieContainer;
currentKieContainer = compilationResult.getKieContainer();

// Dispose old container to free memory
if (oldContainer != null && oldContainer != currentKieContainer) {
  try {
    log.info("Disposing old KieContainer to free memory (prevents memory leak)");
    oldContainer.dispose();
    log.debug("Old KieContainer disposed successfully");
  } catch (Exception e) {
    log.warn("Error disposing old KieContainer: {}", e.getMessage());
  }
}
```
- **Impact**: Prevents OOM crashes, enables indefinite runtime
- **Root Cause**: After 50-100 rule refreshes → 1-10GB leaked → Exit code 137 (SIGKILL)

## 3. 🏗️ Code Architecture & Design Decisions

### Architecture Overview
The Drools Rule Engine Microservice follows a layered architecture:
```
┌─────────────────────────────────────────┐
│         REST API Layer (Port 8080)      │
│  RuleExecutionController, AdminController│
│         MemoryController (NEW)          │
└─────────────────┬───────────────────────┘
                  │
┌─────────────────▼───────────────────────┐
│          Service Layer                   │
│  DroolsEngineService, RuleExecutor       │
│  RuleCompiler                            │
└─────────────────┬───────────────────────┘
                  │
┌─────────────────▼───────────────────────┐
│      Caching Layer (Multi-tier)          │
│  S3 → Redis → Local LRU → KieBase        │
└─────────────────┬───────────────────────┘
                  │
┌─────────────────▼───────────────────────┐
│       Storage Layer                      │
│  S3RuleStorage, InMemoryStorage          │
└──────────────────────────────────────────┘
```

### Key Design Decisions This Session

#### Decision 1: Maven Enforcer Plugin for Java Version
**Problem**: Developer environment might use wrong Java version
**Options Considered**:
1. Manual documentation only (rejected - error-prone)
2. Shell script only (rejected - doesn't prevent Maven builds)
3. Maven Enforcer Plugin ✅ (chosen - automatic enforcement)

**Decision**: Use Maven Enforcer Plugin
**Rationale**:
- Fails build immediately if wrong Java version
- Clear error message guides developer
- Works in CI/CD pipelines
- No way to accidentally bypass

**Trade-offs**:
- Adds ~50ms to build time (negligible)
- Another plugin dependency (minimal risk)

#### Decision 2: KieContainer Disposal Strategy
**Problem**: Old KieContainer instances accumulate in memory
**Options Considered**:
1. Keep old containers cached (rejected - memory leak)
2. Dispose immediately in foreground ✅ (chosen - simple, effective)
3. Dispose in background thread (rejected - unnecessary complexity)
4. Use weak references (rejected - unpredictable GC timing)

**Decision**: Dispose immediately in foreground with try-catch
**Rationale**:
- Simple and predictable
- Disposal is fast (<10ms typically)
- Try-catch ensures no failures
- Logs provide visibility

**Trade-offs**:
- Slight delay during rule refresh (~5-10ms)
- Could block rule execution briefly (acceptable - rare operation)

#### Decision 3: Memory Monitoring Approach
**Problem**: Need visibility into memory usage
**Options Considered**:
1. External APM only (rejected - requires setup)
2. Metrics export to Prometheus (future - not immediate)
3. REST API endpoint ✅ (chosen - immediate value)
4. JMX monitoring (rejected - harder to use)

**Decision**: Create REST API endpoint with comprehensive stats
**Rationale**:
- Immediate value - no external tools needed
- Easy to curl/monitor
- Provides warnings automatically
- Complements future Prometheus integration

**Trade-offs**:
- Another endpoint to maintain
- Not a replacement for proper APM
- Need to poll manually (vs push to metrics system)

### Design Patterns Applied

**1. Singleton Pattern**: KieContainer Management
- Single `volatile KieContainer currentKieContainer`
- Thread-safe access via read/write locks
- Prevents multiple KieContainer instances

**2. Strategy Pattern**: Storage Abstraction
- `RuleStorage` interface
- Multiple implementations (S3, Local, InMemory)
- `StorageFactory` selects implementation

**3. Decorator Pattern**: Multi-tier Caching
- S3 → Redis → LRU → KieBase
- Each layer wraps the next
- Transparent to callers

**4. Observer Pattern**: Metrics Tracking
- `MeterRegistry` observes all operations
- Metrics collected without business logic changes
- Micrometer abstraction for vendor neutrality

### Critical Code Paths

**Rule Execution Flow** (Hot Path):
```
1. RuleExecutionController.executeRule()
2. DroolsEngineService.executeRule()
3. Check rule exists in loadedRules map
4. Get KieSession from currentKieContainer
5. RuleExecutor.executeRule() with timeout
6. Return result
```
**Performance**: P99 < 100ms (cached rules)

**Rule Refresh Flow** (Cold Path):
```
1. AdminController.refreshRules()
2. DroolsEngineService.loadRules()
3. Write lock acquired
4. RuleCompiler.compileRules()
5. Get new KieContainer
6. Dispose old KieContainer ← NEW (prevents memory leak)
7. Update loadedRules map
8. Write lock released
```
**Frequency**: Rare (manual trigger or scheduled)

### Memory Management Architecture

**Before Fix**:
```
Rule Refresh → New KieContainer created
                Old KieContainer orphaned
                No disposal
                Garbage Collector can't collect (references held)
                Memory leak: +10-100MB per refresh
```

**After Fix**:
```
Rule Refresh → New KieContainer created
                Old KieContainer reference saved
                oldContainer.dispose() called
                Resources freed immediately
                Garbage Collector can collect
                Memory stable: no leak
```

## 8. 💡 Knowledge Capture

### Technical Insights Gained

**1. KieContainer Memory Management**
```java
// KEY LEARNING: KieContainer.dispose() MUST be called
// KieContainer holds:
// - Compiled KieBase (10-100MB per container)
// - ClassLoader with rule classes
// - Internal Drools data structures
// Without dispose(), these are NEVER freed
```

**Pattern**: Always dispose old KieContainer before replacing:
```java
KieContainer old = current;
current = newContainer;
if (old != null && old != current) {
    old.dispose();  // Critical for memory management
}
```

**2. Exit Code 137 Diagnosis**
```
Exit Code = Signal Number + 128
137 = 9 (SIGKILL) + 128
SIGKILL from OS = Out of Memory kill
```

**Pattern**: When investigating crashes:
1. Check exit code
2. Code 137 → Look for memory leaks
3. Review object lifecycle (create/dispose)
4. Check for object accumulation

**3. Maven Enforcer Plugin Benefits**
```xml
<!-- Prevents subtle bugs from Java version mismatches -->
<requireJavaVersion>
    <version>[17,18)</version>  <!-- [min, max) -->
</requireJavaVersion>
```

**Pattern**: Always enforce build requirements at build time:
- Java version
- Maven version
- Plugin versions
- Dependency versions

**4. G1GC Tuning for Drools**
```
-XX:+UseG1GC                    # Good for large heaps
-XX:MaxGCPauseMillis=200        # Keep pauses short
-XX:+UseStringDeduplication     # Drools has many strings
```

**Pattern**: Drools-specific JVM tuning:
- Large heap needed (1-2GB minimum)
- G1GC handles it well
- String deduplication saves memory
- Monitor with GC logs

### Patterns and Best Practices

**Pattern 1: Resource Lifecycle Management**
```
CREATE → USE → DISPOSE
- Always pair creation with disposal
- Track ownership clearly
- Dispose in reverse order of creation
- Handle disposal errors gracefully
```

**Pattern 2: Defensive Memory Monitoring**
```java
// Monitor memory proactively
GET /admin/memory/info

// Set warnings at multiple thresholds
if (usage > 90%) -> CRITICAL
if (usage > 80%) -> WARNING
if (usage > 70%) -> CAUTION

// React before OOM occurs
```

**Pattern 3: Build-Time Validation**

**Pattern 4: Multi-Layered Diagnostics**
```
1. Application logs (what happened)
2. Metrics (quantitative data)
3. Heap dumps (deep inspection)
4. GC logs (memory behavior)
5. Thread dumps (concurrency issues)
```

### Anti-Patterns Identified

**Anti-Pattern 1: Silent Resource Replacement**
```java
// WRONG - Silently leaks old container
currentKieContainer = newKieContainer;

// RIGHT - Explicitly dispose old
KieContainer old = currentKieContainer;
currentKieContainer = newKieContainer;
old.dispose();
```

**Anti-Pattern 2: Assuming Garbage Collection**
```java
// WRONG - Assuming GC will clean up
oldContainer = null;  // Still has references elsewhere!

// RIGHT - Explicit resource management
oldContainer.dispose();  // Free resources immediately
```

**Anti-Pattern 3: No Build-Time Validation**
```bash
# WRONG - Only documentation
# "Please use Java 17"

# RIGHT - Automated enforcement
maven-enforcer-plugin enforces Java 17
```

**Anti-Pattern 4: Post-Mortem Debugging Only**
```bash
# WRONG - Wait for OOM, then investigate
# No heap dumps configured
# No GC logs
# No memory monitoring

# RIGHT - Proactive monitoring
# Heap dumps on OOM
# GC logs enabled
# Memory monitoring endpoint
# Alerts before OOM
```

### Gotchas and Pitfalls

**Gotcha 1: Maven Inherits Java from PATH**
- `mvn --version` uses Java from PATH, not JAVA_HOME
- Solution: Set JAVA_HOME explicitly
- Verify: Check Maven output shows correct Java

**Gotcha 2: KieContainer Has Hidden Memory**
- Visible object size: ~1MB
- Actual memory used: 10-100MB (ClassLoader, compiled rules)
- Solution: Always dispose explicitly

**Gotcha 3: Docker Compose Volume Mounts**
- Must create directory before mount
- Otherwise Docker creates it as root
- Solution: `mkdir -p heap-dumps gc-logs`

**Gotcha 4: Long JVM Options in YAML**
- Can't split across lines easily
- Must be single environment variable
- Solution: Accept long line or use .env file

```java
public boolean loadRules(List<Rule> rules) {
    rulesLock.writeLock().lock();
    try {
        // Compile rules
        CompilationResult result = compiler.compileRules(rules);

        // Dispose old container
        KieContainer old = currentKieContainer;
        currentKieContainer = result.getKieContainer();

        if (old != null && old != currentKieContainer) {
            try {
                log.info("Disposing old KieContainer");
                old.dispose();
            } catch (Exception e) {
                log.warn("Error disposing: {}", e.getMessage());
            }
        }

        return true;
    } finally {
        rulesLock.writeLock().unlock();
    }
}
```

```java
private List<String> getMemoryWarnings(double heapPercent) {
    List<String> warnings = new ArrayList<>();

    if (heapPercent > 90) {
        warnings.add("CRITICAL: Heap > 90% - OOM risk HIGH!");
    } else if (heapPercent > 80) {
        warnings.add("WARNING: Heap > 80% - increase heap size");
    } else if (heapPercent > 70) {
        warnings.add("CAUTION: Heap > 70% - monitor closely");
    }

    return warnings;
}
```

**Snippet 3: Memory Monitoring Endpoint**
```java
@GetMapping("/admin/memory/info")
public Map<String, Object> getMemoryInfo() {
    MemoryMXBean memory = ManagementFactory.getMemoryMXBean();
    MemoryUsage heap = memory.getHeapMemoryUsage();

    Map<String, Object> info = new HashMap<>();
    info.put("heapUsedMB", heap.getUsed() / 1024 / 1024);
    info.put("heapMaxMB", heap.getMax() / 1024 / 1024);
    info.put("heapPercent", (heap.getUsed() * 100.0) / heap.getMax());
    info.put("warnings", getWarnings(info));

    return info;
}
```
